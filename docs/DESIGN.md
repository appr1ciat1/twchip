# twchip 設計文件

台股籌碼資料庫：三大法人、外資持股、個股日成交、券商分點。
原則只有一條：**沒有通過驗證的資料不發布。**

## 1. 為什麼重做

舊專案（tw-institutional-stocker）的錯誤有一個共同根源：抓到什麼就存什麼，事後才補驗證。
具體表現為：休市日存了他日資料、比率欄解析成 0 卻沒人發現、CI 因時區判斷失敗而永久漏資料。

新專案把順序反過來：

```
抓取 → 原始回應永久保存 → 解析 → 單表檢查 → 跨表檢查 → 全部通過才寫入 curated
                                                      └─ 任一阻擋性檢查失敗 → quarantine + 告警
```

## 2. 資料集

| 資料集 | 來源 | 粒度 | 可回補歷史 | 主鍵 |
|---|---|---|---|---|
| `calendar` | TWSE 休市表 + 當日行情是否存在 | 日 | 是 | date |
| `quotes` | TWSE MI_INDEX、TPEX afterTrading/otc | 日 × 股票 | 是 | date, market, code |
| `inst_flows` | TWSE T86、TPEX insti/dailyTrade | 日 × 股票 | 是 | date, market, code |
| `foreign_holdings` | TWSE MI_QFIIS、TPEX insti/qfii | 日 × 股票 | 是 | date, market, code |
| `broker_top` | 富邦 e-Broker（MoneyDJ）主力進出 | 日 × 股票 × 方向 × 名次 | **是**（`e=f=日期` 單日查詢） | date, code, side, rank |
| `broker_top_summary` | 同上頁尾 | 日 × 股票 | 是 | date, code |
| `broker_bsr` | 證交所買賣日報表 | 日 × 股票 × 分點 × 價位 | 否（只有當日，需人工輸入驗證碼） | date, code, seq |

設計決策：

- **保留官方所有欄位。** 例如三大法人保留每一類的買進、賣出、買賣超與官方合計。舊專案只存淨額，因此無法做恆等式與上限檢查。
- **單位以官方為準。** 股就存股，張就存張，欄位名帶單位後綴（`_shares`、`_lots`）。
- **缺值是 NULL。** 永不補 0。

## 3. 交易日曆：對齊的基礎

所有資料集以 `date` 對齊。錯一天，所有跨表檢查都會失效，所以日曆是第一個要做對的東西。

判定規則：

1. 週末：休市。
2. 證交所休市表列出的日期：休市。
3. 其他平日：以「當日行情是否存在」為準。上市與上櫃行情都為空，且已過隔日，才判定為臨時休市（颱風）。
4. 休市表與實際行情矛盾時（表上休市卻有行情，或反之）：阻擋並告警。

日曆本身也是一個檢查：任何資料集若在休市日有資料，或在交易日缺資料，都會被抓出。

## 4. 驗證與對齊矩陣

`B` = 阻擋性（不通過就不發布），`W` = 警告（發布但記錄）。

### 4.1 每個來源都做的檢查

| ID | 檢查 | 等級 | 抓得到的錯誤 |
|---|---|---|---|
| G1 | 回應日期 = 請求日期 | B | 他日資料存成當日（舊專案 5/1、6/19） |
| G2 | 欄位名稱完全符合預期 | B | 官方改版、欄位錯抓（舊專案 dealer 全 0） |
| G3 | 主鍵唯一、無 NULL | B | 重複列 |
| G4 | 列數在近 20 日中位數 ±15% | B | 截斷、部分失敗 |
| G5 | 當日指紋 ≠ 前一交易日指紋 | B | 端點忽略日期回傳舊快照（舊專案 TPEX 外資 43 天） |
| G6 | 休市日無資料、交易日有資料 | B | 時區錯、日曆錯 |

### 4.2 `quotes`

| ID | 檢查 | 等級 |
|---|---|---|
| Q1 | 有成交時 最低 ≤ 開、收 ≤ 最高 | B |
| Q2 | 收盤 − 漲跌價差 = 前一交易日收盤 | W（除權息、新上市例外） |
| Q3 | 漲跌幅 ≤ 10.5% | W |
| Q4 | 成交金額 / 成交股數 落在 [最低, 最高] | B |

### 4.3 `inst_flows`

| ID | 檢查 | 等級 |
|---|---|---|
| F1 | 每一類 買進 − 賣出 = 買賣超 | B |
| F2 | 外資合計 = 外資(不含自營) + 外資自營；自營合計 = 自行買賣 + 避險 | B |
| F3 | 外資 + 投信 + 自營 = 官方三大法人合計 | B |
| F4 | **跨表**：每一類買進股數、賣出股數 ≤ 當日成交股數 | B |
| F5 | **跨表**：有法人交易的股票必須出現在 `quotes` | W |

F4 是最強的日期對齊檢查：若抓到他日資料，大量股票的法人買進會超過當日成交量。

### 4.4 `foreign_holdings`

| ID | 檢查 | 等級 |
|---|---|---|
| H1 | 持股比率 = 持有股數 / 發行股數（±0.01%） | B |
| H2 | 持有股數 ≤ 發行股數；比率 ∈ [0, 投資上限] | B |
| H3 | **跨表**：Δ持股（D 對 D−1）與 D 日外資買賣超同號率 ≥ 0.80 | B |
| H4 | **跨表**：同號率對 D−1、D+1 日買賣超明顯較低（無日期錯位） | W |
| H5 | 發行股數與前日相同，或變動檔數 < 1% | W |

H3 在舊專案上的實測：正常日中位數 0.93 至 0.96，錯誤日 0.58。

### 4.5 `broker_top`（富邦）

| ID | 檢查 | 等級 |
|---|---|---|
| T1 | 頁面「最後更新日」= 請求日期 | B |
| T2 | 買超、賣超各 15 列（成交稀少的股票可少於 15） | B |
| T3 | 買進 − 賣出 = 買賣超 | B |
| T4 | 15 列加總 = 頁尾「合計買超／賣超張數」 | B |
| T5 | **跨表**：隱含成交量 = 買賣超 ÷ 佔成交比重，與 `quotes` 成交張數差距 ≤ 3% | B |
| T6 | **跨表**：頁尾平均成本落在當日 [最低, 最高] | B |
| T7 | 名次依張數遞減（容許 1 張四捨五入誤差） | W |
| T8 | 分點代號（BHID）與名稱對照穩定；變更時寫入分點主檔 | W |
| T9 | **外部真值**：抽樣股票與證交所日報表彙總後逐列相符 | B（被抽到的那檔） |

T5 已在舊資料驗證：佔成交比重的分母就是當日成交量，同股同日內隱含成交量離散中位數 1.7%。

### 4.6 `broker_bsr`（證交所日報表，真值）

| ID | 檢查 | 等級 |
|---|---|---|
| R1 | 全分點買進股數合計 = 賣出股數合計 = 當日成交股數 | B |
| R2 | 每個價位落在當日 [最低, 最高] | B |
| R3 | Σ(價格 × 股數) 與 `quotes` 成交金額差距 ≤ 0.1% | W |

R1 是市場結清恆等式，是整個專案中最強的單一檢查。

## 5. 外部真值與第二來源

| 資料集 | 真值或第二來源 | 用法 |
|---|---|---|
| inst_flows | 富邦 zgk 法人買賣超排行 | 每週稽核，抽前 50 名比對 |
| broker_top | 證交所買賣日報表 | 每日人工抽 2~3 檔（需輸入驗證碼） |
| broker_top | 富邦頁面重抓 | 每週隨機重抓過去 10 個 (日, 股)，偵測廠商事後改寫 |
| 全部 | 舊專案資料 | 匯入為 `legacy`，與官方重抓逐列比對，結果寫入稽核報告 |

**不做的事**：自動辨識證交所驗證碼。驗證碼的目的是阻擋自動化，繞過它有使用條款與法律風險。日報表改為「人工輸入驗證碼的每日抽樣稽核」。

## 6. 儲存佈局（私有 Hugging Face dataset）

```
raw/{source}/{YYYY}/{YYYYMMDD}/{key}__{sha12}.{ext}.gz    原始回應，只增不改
curated/{dataset}/{YYYY}/{YYYY-MM-DD}.parquet             每個交易日一檔，通過驗證才寫入
quarantine/{dataset}/{YYYY-MM-DD}.parquet                 未通過驗證，附報告
quality/{YYYY}/{YYYY-MM-DD}.json                          當日全部檢查結果
meta/calendar.parquet, meta/broker_master.parquet          日曆、分點主檔
legacy/                                                   舊專案資料（含出處），只讀
```

每日一檔的理由：重跑某日只會整檔替換，天然冪等；HF commit 小；任一日可單獨稽核。

## 7. 每日排程（GitHub Actions）

舊專案的致命傷是「用執行當下的台北日期判斷目標日」，排程延遲 5 小時就跨日失敗。

新設計：

- **排程**：平日台北 16:17 到隔日 00:17 每小時一次，加上週六補跑。重複執行無害。
- **待辦清單由資料狀態決定**：`pending = 日曆上的交易日 − 已通過驗證的 (資料集, 日期)`。與執行時間無關。
- **尚未公布 ≠ 失敗**：官方還沒出資料就留到下一小時，不報錯。
- **超過時限才告警**：某交易日超過 30 小時仍未通過，工作流程失敗，GitHub 寄信。
- **資料集互相獨立**：券商分點不再因三大法人失敗而跳過。

## 8. 舊資料的處理

舊專案的資料不直接當真值。流程是：

1. 匯入 `legacy/`，保留出處（commit、品質旗標）。
2. 以官方端點重抓同一期間，進入正常驗證流程。
3. 逐列比對 legacy 與重抓結果，差異寫入稽核報告。

這樣「累積的資料」本身也被驗證了一次。券商分點過去缺的 38 天，用富邦單日查詢補回。
