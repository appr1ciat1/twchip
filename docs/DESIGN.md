# twchip 設計文件

台股籌碼資料庫：三大法人、外資持股、個股日成交、券商分點。
原則只有一條：**沒有通過驗證的資料不發布。**

## 1. 為什麼重做

舊專案（tw-institutional-stocker）的錯誤有一個共同根源：抓到什麼就存什麼，事後才補驗證。
具體表現為：休市日存了他日資料、比率欄解析成 0 卻沒人發現、CI 因時區判斷失敗而永久漏資料。

新專案把順序反過來：

```
抓取 → 原始回應永久保存 → 解析 → 單表檢查 → 跨表檢查 → 全部通過才寫入 curated
                                                      └─ 任一阻擋性檢查失敗 → quarantine + 告警
```

## 2. 資料集

| 資料集 | 來源 | 粒度 | 可回補歷史 | 主鍵 |
|---|---|---|---|---|
| `calendar` | TWSE 休市表 + 當日行情是否存在 | 日 | 是 | date |
| `quotes` | TWSE MI_INDEX、TPEX afterTrading/otc | 日 × 股票 | 是 | date, market, code |
| `inst_flows` | TWSE T86、TPEX insti/dailyTrade | 日 × 股票 | 是 | date, market, code |
| `foreign_holdings` | TWSE MI_QFIIS、TPEX insti/qfii | 日 × 股票 | 是 | date, market, code |
| `block_trades` | TWSE 鉅額交易日成交資訊（BFIAUU，單一證券） | 日 × 成交 | 是 | date, market, code, seq |
| `broker_top` | 富邦 e-Broker（MoneyDJ）主力進出 | 日 × 股票 × 方向 × 名次 | **是**（`e=f=日期` 單日查詢） | date, code, side, rank |
| `broker_top_summary` | 同上頁尾 | 日 × 股票 | 是 | date, code |
| `broker_bsr` | 證交所買賣日報表 | 日 × 股票 × 分點 × 價位 | 否（只有當日，需人工輸入驗證碼） | date, code, seq |

設計決策：

- **保留官方所有欄位。** 例如三大法人保留每一類的買進、賣出、買賣超與官方合計。舊專案只存淨額，因此無法做恆等式與上限檢查。
- **單位以官方為準。** 股就存股，張就存張，欄位名帶單位後綴（`_shares`、`_lots`）。
- **缺值是 NULL。** 永不補 0。
- **收錄範圍以代號格式定義。** 代號須符合 `^\d{4,6}[A-Z]{0,2}$`（一般股票、ETF、多數特別股、存託憑證）。
  不符合的證券（例：台新金特別股 2887Z1）不收錄行情、法人與外資持股。2026-11-04 決定維持此範圍。
  鉅額交易照樣保存這類證券的成交，K2b 會記錄。

## 3. 交易日曆：對齊的基礎

所有資料集以 `date` 對齊。錯一天，所有跨表檢查都會失效，所以日曆是第一個要做對的東西。

判定規則：

1. 週末：休市。
2. 證交所休市表列出的日期：休市。
3. 其他平日：以「當日行情是否存在」為準。上市與上櫃行情都為空，且已過隔日，才判定為臨時休市（颱風）。
4. 休市表與實際行情矛盾時（表上休市卻有行情，或反之）：阻擋並告警。

日曆本身也是一個檢查：任何資料集若在休市日有資料，或在交易日缺資料，都會被抓出。

## 4. 驗證與對齊矩陣

`B` = 阻擋性（不通過就不發布），`W` = 警告（發布但記錄）。

### 4.1 每個來源都做的檢查

| ID | 檢查 | 等級 | 抓得到的錯誤 |
|---|---|---|---|
| G1 | 回應日期 = 請求日期 | B | 他日資料存成當日（舊專案 5/1、6/19） |
| G2 | 欄位名稱完全符合預期 | B | 官方改版、欄位錯抓（舊專案 dealer 全 0） |
| G3 | 主鍵唯一、無 NULL | B | 重複列 |
| G4 | 列數在近 20 日中位數 ±15% | B | 截斷、部分失敗 |
| G5 | 當日指紋 ≠ 前一交易日指紋 | B | 端點忽略日期回傳舊快照（舊專案 TPEX 外資 43 天） |
| G6 | 休市日無資料、交易日有資料 | B | 時區錯、日曆錯 |

### 4.2 `quotes`

| ID | 檢查 | 等級 |
|---|---|---|
| Q1 | 有成交時 最低 ≤ 開、收 ≤ 最高 | B |
| Q2 | 收盤 − 漲跌價差 = 前一交易日收盤 | W（除權息、新上市例外） |
| Q3 | 漲跌幅 ≤ 10.5% | W |
| Q4 | 成交金額 / 成交股數 落在 [最低, 最高] | B |

### 4.3 `inst_flows`

| ID | 檢查 | 等級 |
|---|---|---|
| F1 | 每一類 買進 − 賣出 = 買賣超 | B |
| F2 | 外資合計 = 外資(不含自營) + 外資自營；自營合計 = 自行買賣 + 避險 | B |
| F3 | 外資 + 投信 + 自營 = 官方三大法人合計 | B |
| F4 | **跨表**：每一類買進股數、賣出股數 ≤ 當日成交股數；超量檔數比例 ≤ 門檻（見 §4.6） | B |
| F5 | **跨表**：有法人交易的股票必須出現在 `quotes` | W |

F4 是最強的日期對齊檢查：若抓到他日資料，大量股票的法人買進會超過當日成交量。

### 4.4 `foreign_holdings`

| ID | 檢查 | 等級 |
|---|---|---|
| H1 | 持股比率 = 持有股數 / 發行股數（±0.01%） | B |
| H2 | 持有股數 ≤ 發行股數；比率 ∈ [0, 投資上限] | B |
| H3 | **跨表**：Δ持股（D 對 D−1）與 D 日外資買賣超同號率 ≥ 0.80 | B |
| H4 | **跨表**：同號率對 D−1、D+1 日買賣超明顯較低（無日期錯位） | W |
| H5 | 一般股票發行股數變動檔數 < 1%（不含 ETF、存託憑證；它們每天申購買回） | W |

H3 在舊專案上的實測：正常日中位數 0.93 至 0.96，錯誤日 0.58。

### 4.5 `broker_top`（富邦）

| ID | 檢查 | 等級 |
|---|---|---|
| T1 | 頁面「最後更新日」= 請求日期 | B |
| T2 | 買超、賣超各 15 列（成交稀少的股票可少於 15） | B |
| T3 | 買進 − 賣出 = 買賣超 | B |
| T4 | 15 列加總 = 頁尾「合計買超／賣超張數」 | B |
| T5 | **跨表**：隱含成交量 = 買賣超 ÷ 佔成交比重。今日「隱含量 ÷（官方成交張數 − 鉅額交易）」與該股近 20 日中位數的相對偏離 ≤ 門檻（見 §4.6） | W |
| T6 | **跨表**：頁尾平均成本落在當日 [最低, 最高] | B |
| T7 | 名次依張數遞減（容許 1 張四捨五入誤差） | W |
| T8 | 分點代號與名稱對照穩定；變更時寫入分點主檔 | W |
| T9 | **外部真值**：抽樣股票與證交所日報表彙總後逐列相符 | B（被抽到的那檔） |

T5 已在舊資料驗證：佔成交比重的分母就是當日成交量，同股同日內隱含成交量離散中位數 1.7%。

**T5 的實測修正（2026-11-01 probe）。** 富邦的分母和官方成交股數口徑不同，而且每檔不同：
2330 隱含量比官方少 4.7%，6488 多 10.3%。因此 T5 改為：

- 歷史 ≥ 10 日：比較「今日比值」與「該股前 20 個交易日比值中位數」，固定偏差互相抵消。
- 歷史不足：退回直接比較，只警告。
- 等級預設 W。用 `scripts/analyze_backfill.py` 看完回補資料的偏離分布後，
  在 GitHub Variables 設定 `TWCHIP_T5_REL_TOL`（門檻）與 `TWCHIP_T5_LEVEL=B`（改為阻擋）。

F4 的門檻可依市場分開設定 `TWCHIP_F4_TOL_TWSE`、`TWCHIP_F4_TOL_TPEX`，或用 `TWCHIP_F4_TOL` 同時設定兩個市場。
預設值見 §4.6。

**校正結果（2026-11-03，273 個交易日，校正集 ≤ 2026-06-30）。**

- F4 上市：273 天全部是 0。門檻 0.5%，錯位偵測率 100%。
- F4 上櫃：正常最高 1.8%（櫃買行情的成交股數不含盤後定價）。門檻 3%，錯位偵測率 100%。
- T5（扣除鉅額交易**之前**）：沒有任何門檻能讓誤報率 ≤ 0.2%（門檻 20% 時仍有 0.47%）。之後的結論見 §4.6。
- H3：上市、上櫃都維持 0.80（校正前即已設定）。驗證集零誤報，錯位偵測率 100%。
- T5 偏離的主因已確認：證交所每日收盤行情的成交股數**包含鉅額交易**，富邦的分母不含。
  偏離最大的 12 筆中，8 筆扣除單一證券鉅額交易後，比值回到 1 ± 0.1%。
  其餘 4 筆（2412 2025-09-30、2330 2026-06-01 與 2026-09-01、2891 2026-08-28）扣除鉅額與盤後定價後仍偏低 7%~40%，
  原因未明，可能是富邦當日佔比的分母本身有誤。
- 因此新增 `block_trades` 資料集，T5 改用「官方成交股數 − 鉅額交易」。鉅額交易未發布的日子 T5 只警告。

### 4.5b `block_trades`

| ID | 檢查 | 等級 |
|---|---|---|
| K1 | 成交金額 = 成交價 × 成交股數（容許 1 元） | B |
| K2 | 有鉅額交易的股票都有當日行情（本專案範圍內） | B |
| K2b | 鉅額交易中有範圍外的證券（代號不符 `CODE_RE`，例：特別股 2887Z1） | W |
| K3 | 每檔鉅額成交股數 ≤ 當日成交股數（官方成交股數包含鉅額交易） | B |
| K4 | 各筆成交股數加總 = 官方「總計」；成交金額差距 ≤ 0.5 元 ×（列數 + 1）（各列與總計各自四捨五入） | B |

官方報表最後一列是「總計」。解析時把它拿出來當 K4 的官方值，不當成一筆交易。
（第一次回補時沒有處理這一列，273 天全被 K2 擋下，沒有發布任何錯誤資料。）

鉅額交易可能整天都沒有。行情已發布且已過隔日 0 時仍無資料，記為「當日無鉅額交易」並發布空檔。
不做列數檢查（G4），因為每天筆數差異很大（實測 22~92 筆）。

### 4.6 門檻的選擇規則與目前的值

**選擇規則。** 看資料之前先定好，實作在 `scripts/calibrate.py`，看完結果不再改：

1. 切分：校正集 = 交易日 ≤ 2026-06-30，只用它決定門檻；驗證集 = 之後，只用來檢驗。
2. 正常配對：D 日的資料互相比對。錯誤配對：D 日資料配上 D±1、±2、±5 個交易日的資料，模擬「抓到他日資料」。
   誤報率 = 正常配對被判失敗的比例；偵測率 = 錯誤配對被判失敗的比例。
3. 門檻依樣本數分兩種選法：
   - 每檔每日的檢查（T5，樣本數千筆）：校正集誤報率 ≤ 0.2% 的最嚴格值。
   - 每市場每日的檢查（F4、H3，樣本約 180 筆）：0.2% 從這麼少的樣本估不準，改為「校正集零誤報」，
     且與最差正常值保持安全距離（F4：門檻 ≥ 最大值 × 1.5；H3：門檻 ≤ 最小值 − 0.05）。
   - 兩種都要求驗證集誤報率 ≤ 0.5%。
4. T5 要改成阻擋，驗證集偵測率還必須 ≥ 80%。
5. 校正集裡超過門檻的正常資料逐筆列出，人工查原始頁面。

**目前的值（2026-11-05 起生效）。** 程式預設值就是正式值。GitHub Variables 只用來臨時調整：有設定就覆寫預設，被刪除或留空就退回正式值，不會悄悄放寬。F4 的優先順序是 `TWCHIP_F4_TOL_{市場}` → `TWCHIP_F4_TOL`（兩個市場共用）→ 依市場的正式值。

| 檢查 | Variable | 正式值 | 程式預設 | 等級 |
|---|---|---|---|---|
| F4 上市 | `TWCHIP_F4_TOL_TWSE` | 0.005（0.5%） | 0.005 | B |
| F4 上櫃 | `TWCHIP_F4_TOL_TPEX` | 0.03（3%） | 0.03 | B |
| T5 門檻 | `TWCHIP_T5_REL_TOL` | 0.15（15%） | 0.15 | W |
| T5 等級 | `TWCHIP_T5_LEVEL` | W | W | W |
| H3 | （程式內固定） | 0.80 | 0.80 | B |

T5 在該股歷史不足 10 個交易日時，退回直接比較「隱含量 ÷ 官方量 − 1」，門檻是 `TWCHIP_BROKER_VOLUME_TOL`（預設 3%），一律只警告。

**依據（2025-09-11 至 2026-10-30，273 個交易日）。**

- **F4 上市 0.5%。** 273 天每天都是 0 檔超量，是很乾淨的恆等式。0.5% 下錯位偵測率 100%。
- **F4 上櫃 3%。** 正常日最高 1.8%，原因是櫃買行情的成交股數不含盤後定價、法人買賣有含。
  1.8% × 1.5 = 2.7% ≤ 3%，符合安全距離。校正集零誤報，錯位偵測率 100%。
  驗證集有 1 天超過（2026-09-18，超量 15.5%，1/82 天 = 1.22%），高於 0.5% 的要求。
  人工查過原始資料，確認是官方的正確資料，以 `waivers.json` 豁免（§4.7）。
  決定：**維持 3%、阻擋**。寧可偶爾多擋一天再人工確認，也不放過錯誤資料。依目前頻率，一年約 3 次需要人工查核。
- **T5 15%、只警告。** 扣除鉅額交易後重新校正：

  | 門檻 | 資料 | 校正集誤報率 | 驗證集誤報率 | 驗證集偵測率 |
  |---|---|---|---|---|
  | 3% | 扣除前 | 10.06% | 10.73% | — |
  | 3% | 扣除後 | 1.30% | 1.95% | — |
  | **15%** | **扣除後** | **0.138%** | **0.305%** | **77.1%** |

  15% 是校正集誤報率 ≤ 0.2% 的最嚴格值，驗證集 0.305% ≤ 0.5%，兩項通過。
  但偵測率 77.1% < 80%，依規則 4 **不能改成阻擋**。這是照事先定好的規則判出來的，不是看完數字才決定。
  以追蹤 20 檔股票換算，正常資料約每 36 個交易日（校正集）到每 16 個交易日（驗證集）出現 1 次 T5 警告。
- **T5 仍偏離的正常資料集中在少數日子。** 2026-03-31 有 2330、2881、2891，2026-06-01 有 2330、2345。
  不同股票在同一天一起偏離，代表原因在「那一天」而不是個別股票。3/31 是季底。
  推論：證券組合鉅額交易（一籃子股票一起成交），單一證券鉅額報表不含這類交易。**尚未驗證。**
- **H3 0.80。** 校正前就依舊專案資料設定。上市、上櫃驗證集都零誤報，錯位偵測率 100%。

**待用新資料驗證（2026-11-05 之後的資料才算數）。** 下面兩個改法都是看過舊資料才想到的，
用同一批資料驗證會高估效果，所以要等每日更新累積一到兩個月的新資料：

- **T5 改用不對稱門檻。** 正常資料的偏離幾乎都是負的，最大只有 +0.38%：富邦的數字幾乎不會比官方多。
  往上嚴、往下寬，有機會讓偵測率超過 80%，T5 才能改成阻擋。
- **F4 改用相對比較。** 要求當日超量比例明顯低於配前後各日。9/18 就是這種情況：當日 15.5%，配前後各日 25%~40%。
  這樣可以減少人工豁免。
- 同時驗證「證券組合鉅額交易」的推論。

## 4.7 人工豁免（`waivers.json`）

阻擋性檢查未通過時，只有在人工查過原始資料、確認資料正確後，才能豁免。規則：

- 每筆豁免指定 日期 × 單位 × 檢查，並記錄違反筆數上限 `max_n_bad` 與理由。
- 資料若之後改變、違反筆數變多，豁免自動失效，照樣隔離。
- 豁免後的檢查改記為 W，品質報告保留原始結果與理由。
- 豁免清單放在 repo，受版本控制，任何變更都有紀錄。

### 4.6 `broker_bsr`（證交所日報表，真值）

| ID | 檢查 | 等級 |
|---|---|---|
| R1 | 全分點買進股數合計 = 賣出股數合計 = 當日成交股數 | B |
| R2 | 每個價位落在當日 [最低, 最高] | B |
| R3 | Σ(價格 × 股數) 與 `quotes` 成交金額差距 ≤ 0.1% | W |

R1 是市場結清恆等式，是整個專案中最強的單一檢查。

## 5. 外部真值與第二來源

| 資料集 | 真值或第二來源 | 用法 |
|---|---|---|
| inst_flows | 富邦 zgk 法人買賣超排行 | 每週稽核，抽前 50 名比對 |
| broker_top | 證交所買賣日報表 | 每日人工抽 2~3 檔（需輸入驗證碼） |
| broker_top | 富邦頁面重抓 | 每週隨機重抓過去 10 個 (日, 股)，偵測廠商事後改寫 |
| 全部 | 舊專案資料 | 匯入為 `legacy`，與官方重抓逐列比對，結果寫入稽核報告 |

**不做的事**：自動辨識證交所驗證碼。驗證碼的目的是阻擋自動化，繞過它有使用條款與法律風險。日報表改為「人工輸入驗證碼的每日抽樣稽核」。

## 6. 儲存佈局（私有 Hugging Face dataset）

```
raw/{source}/{YYYY}/{YYYYMMDD}/{key}__{sha12}.{ext}.gz    原始回應，只增不改
curated/{dataset}/{YYYY}/{YYYY-MM-DD}.parquet             每個交易日一檔，通過驗證才寫入
quarantine/{dataset}/{YYYY-MM-DD}.parquet                 未通過驗證，附報告
quality/{YYYY}/{YYYY-MM-DD}.json                          當日全部檢查結果
meta/calendar.parquet, meta/broker_master.parquet          日曆、分點主檔
legacy/                                                   舊專案資料（含出處），只讀
```

每日一檔的理由：重跑某日只會整檔替換，天然冪等；HF commit 小；任一日可單獨稽核。

## 7. 每日排程（GitHub Actions）

舊專案的致命傷是「用執行當下的台北日期判斷目標日」，排程延遲 5 小時就跨日失敗。

新設計：

- **排程**：平日台北 16:17 到隔日 00:17 每小時一次，加上週六補跑。重複執行無害。
- **待辦清單由資料狀態決定**：`pending = 日曆上的交易日 − 已通過驗證的 (資料集, 日期)`。與執行時間無關。
- **尚未公布 ≠ 失敗**：官方還沒出資料就留到下一小時，不報錯。
- **超過時限才告警**：某交易日超過 30 小時仍未通過，工作流程失敗，GitHub 寄信。
- **資料集互相獨立**：券商分點不再因三大法人失敗而跳過。

## 8. 舊資料的處理

舊專案的資料不直接當真值。流程是：

1. 匯入 `legacy/`，保留出處（commit、品質旗標）。
2. 以官方端點重抓同一期間，進入正常驗證流程。
3. 逐列比對 legacy 與重抓結果，差異寫入稽核報告。

這樣「累積的資料」本身也被驗證了一次。券商分點過去缺的 38 天，用富邦單日查詢補回。

## 9. 分點代號的定義（2026-11-05 釐清）

富邦連結有兩個代號，意義不同：

| 欄位 | 來源 | 意義 | 例 |
|---|---|---|---|
| `bhid` | 連結的 `BHID` 參數 | 券商**總公司** | 9200（凱基） |
| `broker_b` | 連結的 `b` 參數 | **分點**（含英文字母時以 UTF-16 十六進位編碼） | 9268（凱基-台北） |

- 分點代號用 `fubon.branch_id(broker_b, bhid)` 取得，**區分大小寫**：918G（群益金鼎-新莊）與 918g（群益金鼎-大甲）是不同分點。
  轉大寫會讓 820 個分點撞成 756 個。
- 網站以分點分組。檔名用 `fubon.branch_key`（小寫字母前加底線：918g → 918_g），在不分大小寫的檔案系統也不撞名。
- 券商合併會讓富邦**回溯改寫**歷史頁面的分點代號。例：元富 5920 → 台新 9B20、台新 8150 → 9B17。
  因此「張數相同、只有分點代號不同」記為代號重編（`branch_relabel`），不算數值差異。
- **代號會被重複使用。** 舊資料裡元富同時以 5920 與 9B00 出現；合併後富邦把這些歷史都改標為 9B20（187 列張數完全相同）。
  但 9B00 這個代號在官方資料裡仍然出現。所以同一個代號在不同時期可能代表不同分點，
  不能只靠代號跨來源、跨時間對應。重編對照因此由資料推得，並保守套用：
  舊代號若仍在官方資料中使用，就不視為重編（`legacy._broker_by_branch` 規則 3）。
- **對日後的影響。** 下一次券商合併時：
  - 每週 audit 重抓舊日期，會拿到新代號而與已存資料不符。應該和舊資料比對一樣，把代號重編歸類為警告。**待辦。**
  - 網站的分點歷史與釘選都以代號為鍵，合併前後會斷成兩個分點。網站對找不到的釘選會提示，不會默默消失。
    長期要建一張分點別名表，把重編對照記下來。**待辦。**

## 10. 定稿等待（`settle_hours`）

部分官方資料在當晚先發布未定稿數字，之後才修正。這類單位要等到交易日 0 時之後一段時間才抓。

- 上櫃外資持股：24 小時（隔日 0 時之後）。

  （中位數 0.26%，99% 偏少）；排程延到 23:00 之後或隔日才抓的日子（8/18~8/20、8/28 起）全部吻合。
- 上市外資持股、三大法人在同一時段抓取，與定稿值一致，不需等待。

## 12. 網站保護（2026-11-06）

網站只給自己看。理由是資料授權：證交所網站使用條款規定，散布網站內容需事前書面同意（政府資料開放平臺的資料除外）；
券商分點資料連付費資料商都不得提供給第三人。公開網站等於散布，只有自己登入使用才屬於自行使用。

**做法。** Cloudflare Pages 放靜態網站，Cloudflare Access 擋在前面。

- 登入方式只開 Google，政策只允許指定的 Gmail。登入要 Gmail 密碼與 Google 兩步驟驗證。
- Access 在邊緣節點擋下請求，未登入的人拿不到任何檔案，包括 `data/*.json`。
  靜態網站自己做密碼框沒有用，因為資料檔可以直接下載。
- Access 要同時保護兩組網址：正式網址 `<專案>.pages.dev`，以及預覽網址 `*.<專案>.pages.dev`
  （每次部署都有一個獨立網址，舊的部署網址會一直保留）。
- `_headers` 加 `X-Robots-Tag: noindex`、`robots.txt` 禁止收錄。這是輔助措施，不取代 Access。
- 不使用任何 GitHub artifact。公開 repo 的 artifact，任何 GitHub 使用者都能下載。

**部署的安全順序（`pages.yml`）。** 任何一步沒確認就不部署資料，寧可擋錯也不外洩。

1. 部署不含資料的佔位頁到預覽分支 `guard`。
2. `twchip access-check` 確認正式網址、`guard` 網址、該次部署網址，未登入時都轉到 Access 登入頁（或 401／403）。
   200、404、轉到別處、連線失敗，一律視為「沒有確認受保護」。
3. 通過才產生含資料的網站，部署到正式網址。
4. 部署後再確認一次；失敗就立刻改回佔位頁，工作流程失敗並寄信。

`TWCHIP_SITE_LIVE` 不是 `yes` 時，正式網址只部署佔位頁。第一次設定 Access 時用這個模式。

**驗證。** 單元測試涵蓋判斷規則（包括網域只是開頭或結尾相同的假登入頁）與工作流程的步驟順序。
另外用替身（stub）逐步執行 `pages.yml`，四個情境的結果：

| 情境 | 工作流程 | 部署 |
|---|---|---|
| 尚未開放 | 成功 | 只有佔位頁 |
| 已開放、保護正常 | 成功 | 資料到正式網址 |
| 已開放、保護失效 | 失敗 | 資料從未上傳，正式網址改為佔位頁 |
| 部署後才發現失效 | 失敗 | 資料上傳後立刻改回佔位頁 |

**殘餘風險。** 最後一種情境裡，那一次的部署網址仍保留資料。它屬於 `*.<專案>.pages.dev`，
步驟 2 已確認這組網址受保護，所以只有在 Access 設定剛好在幾秒內被改掉時才會發生。
若真的發生，到 Cloudflare Pages 的部署列表刪除那一次部署。
